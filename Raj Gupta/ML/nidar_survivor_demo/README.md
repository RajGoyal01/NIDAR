# NIDAR AirMouse demo — Phase 7

## Phone-free multi-person professor demo

Run the dashboard-free showcase from the repository root:

```powershell
.\Start-OfflineDemo.ps1
```

It runs the real local YOLO model once on each of six different COCO images and
automatically cycles through verified current-frame counts `1, 2, 4, 6, 4, 6`.
Use `N`/right for the next image, `P`/left for the previous image, `R` to rerun
YOLO on the current image, Space to pause and `Q`/Esc to close. No phone,
dashboard, internet connection or mission database is used.

The displayed `P1...P6` labels are current-picture detection numbers. They are
not persistent `S` identities: persistent identity/duplicate suppression needs
temporally related views of the same people and remains a separate controlled
demo. Read the [offline showcase learning report](../docs/phase_reports/OFFLINE_MULTI_PERSON_SHOWCASE.md).

## Live camera

Start IP Webcam on the phone. Connect the laptop to the same trusted network.
Replace the example address below with the one on the phone:

```powershell
.\.venv\Scripts\python.exe -m nidar_survivor_demo.main --source http://PHONE_IP:8080/video --display-fps 60
```

Press Q/Esc or close the window to stop. `--seconds 30` runs a timed test;
`--headless` measures capture without displaying video. `--source 0` selects a
local webcam; an existing video filename is also supported. Alternatively set
`$env:NIDAR_CAMERA_SOURCE` for the current PowerShell session. URLs are not saved.

`--fps 30` requests webcam FPS / paces local files; it does **not** change a
network camera's settings. `--display-fps 60` is the preview refresh ceiling,
not a claim of 60 camera frames per second. Actual phone FPS/resolution must be
configured in IP Webcam. No audio or video is recorded by this application.

Run tests:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s nidar_survivor_demo/tests -t . -v
```

Read `../docs/phase_reports/PHASE_01_PHONE_STREAM.md` for the architecture,
lag fix, measured results, limitations and manual acceptance checklist.

### Lower-delay IP Webcam mode (current phone)

Actual testing found noticeable delay in continuous MJPEG. The user confirmed
less visible delay with latest-snapshot requests. Use this option for the current
phone; measured throughput was about 8.4 FPS, so it is not yet the smoothness target.

```powershell
.\.venv\Scripts\python.exe -m nidar_survivor_demo.main --source http://PHONE_IP:8080/shot.jpg --transport snapshot --display-fps 60
```

The phone was changed from 1920x1080 to 1280x720 through IP Webcam's local control.
Snapshot mode uses one HTTP request at a time, no continuous video decoder queue.
It requires an HTTP(S) JPEG endpoint; redirects and URL credentials are not
supported. It does not save photos. The existing `/video` mode remains available.

The single-decoder experiment worsened visible delay according to the user;
the default was restored to `--decoder-threads 0` (automatic). It is not the
recommended delay fix.

### Direct MJPEG (experimental; actual-phone latency acceptance failed)

```powershell
.\.venv\Scripts\python.exe -m nidar_survivor_demo.main --source http://PHONE_IP:8080/video --transport mjpeg --display-fps 60
```

This bypasses FFmpeg, drains multipart JPEG data on its own receiver thread,
keeps only the latest compressed image and decodes it with OpenCV. The actual
phone test displayed mostly 20–22 FPS, with one automatic reconnect. It requires
JPEG parts with Content-Length (supported by this IP Webcam). Snapshot remains
the user-confirmed lower-delay fallback. The user still observed seconds of
delay in direct mode after a 720p retest. A wired diagnostic comparison is pending.

## Run the environment check

From PowerShell in the repository root:

```powershell
.\.venv\Scripts\python.exe .\nidar_survivor_demo\check_environment.py --gui
```

The script prints JSON PASS/FAIL records, briefly displays a blank OpenCV window,
and returns exit code 0 only when every selected check passes. It generates and
removes a temporary synthetic video. It does not access the camera or download
model weights. Use `$LASTEXITCODE` immediately afterwards to inspect the result.

## Recreate the environment

Use these commands in a fresh checkout without an existing `.venv`:

```powershell
uv venv --python 3.11 --seed .venv
.\.venv\Scripts\python.exe -m pip install -r .\nidar_survivor_demo\requirements.txt
.\.venv\Scripts\python.exe .\nidar_survivor_demo\check_environment.py --gui
```

`requirements.txt` pins the direct dependencies. `requirements-lock.txt`, once
generated from the verified installation, pins their transitive dependencies too.
For exact package versions, install the lock instead of the direct requirements:

```powershell
.\.venv\Scripts\python.exe -m pip install --extra-index-url https://download.pytorch.org/whl/cu128 -r .\nidar_survivor_demo\requirements-lock.txt
```

The lock targets this Windows/Python 3.11/CUDA 12.8 environment; it is not a promise
of cross-platform compatibility. NVIDIA driver compatibility must also be checked.

Activation is optional when using the explicit interpreter path above. If your
PowerShell policy allows it, activate using `.\.venv\Scripts\Activate.ps1`, then
run `python .\nidar_survivor_demo\check_environment.py`. No machine-wide execution
policy change is needed.
